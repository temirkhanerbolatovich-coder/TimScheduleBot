# Серверное размещение

Требуются Linux с systemd, Python 3.11+, SQLite и системная база часовых поясов. Бот использует исходящие HTTPS-запросы; входящий порт не нужен.

## Первая установка

Передай исходники в закрытый каталог сервера, создай там `.env` из примера, вставь токен и выставь права `0600`. Из каталога исходников запусти `sudo bash deploy/install.sh`. Установщик создаёт пользователя `timschedulebot`, код в `/opt/timschedulebot`, конфигурацию `/etc/timschedulebot.env` и данные `/var/lib/timschedulebot`. Заверши привязку по ссылке из журнала службы, доступного администратору. Удали временную копию `.env` после установки.

Проверь `sudo systemctl status timschedulebot` и затем включи копирование: `sudo systemctl enable --now timschedulebot-backup.timer`. Проверь первую копию и её восстановление в отдельный файл.

## Обновление с Windows

`deploy.ps1` требует SSH-пользователя `ubuntu` с `sudo -n`, доверенного ключа сервера и ключа `$env:USERPROFILE/.ssh/timschedulebot_deploy`. Задай адрес только локально:

```powershell
$env:TIMSCHEDULE_SSH_TARGET = 'ubuntu@your-server'
.\deploy.ps1 -DryRun
.\deploy.ps1
```

DryRun запускает тесты и собирает архив без соединения с сервером. Выпуск проверяет хеш архива, тесты на Linux, создаёт снимок базы и устанавливает код. Обновление systemd unit-файлов не входит в автоматический откат: перед выпуском сохрани их отдельно. Изменения схемы базы также требуют отдельного плана восстановления.

`pull_backup.ps1` скачивает резервную копию в игнорируемый каталог `backups-offsite`. Скрипт требует того же SSH-доступа. Проверь успешность копирования и сохранённый архив перед использованием: не все внешние команды этого скрипта проверяют код возврата. ZIP не зашифрован.

Токен и база не должны попадать в Git. Запускай только один polling-процесс с одним токеном. При переносе с другого сервера сначала останови прежний процесс. Копия на том же диске не защищает от потери сервера.
